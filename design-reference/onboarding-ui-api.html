Vendor Onboarding UI/UX — API Handoff Guide

Context

This document maps every backend API needed to build the 10-step vendor onboarding flow shown in the UI:

  1. Verify Mobile
  2. Enter OTP
  3. Choose Business
  4. Pick Categories
  5. Add Products
  6. Set Prices
  7. Delivery
  8. Payments
  9. Store Settings
  10. You're Live

Use this as a single source of truth for frontend engineers, UI designers, and QA.

Base URL & Authentication

EnvBase URL
Localhttp://localhost:8080/api
Productionhttps://<domain>/api

All endpoints (except business-types list and storefront) require:

Authorization: Bearer <access_token>
Content-Type: application/json

The access_token and refresh_token are returned by Step 2 (POST /v1/auth/verify-otp).

Step 1 — Verify Mobile Number

UI ActionMethodEndpointSource
User enters mobile → clicks Send OTPPOST/v1/auth/request-otpAuthController.java:150-159

Request

{
  "country_code": "+91",
  "mobile_number": "9912149049",
  "user_role": "VENDOR"
}

Validation

  • mobile_number must be exactly 10 digits and start with 6-9.
  • country_code is required.

Response Notes

  • Creates a new user if the mobile is not registered.
  • For user_role: VENDOR, the user is created/updated with the VENDOR authority.
  • Returns mobile_verified: false until OTP is verified.

Response

    "refresh_token": "<long-lived-jwt>",

    "name": null,
    "roles": ["VENDOR"],
    "vendors": [
      {
        "vendor_id": 91,
        "name": "My Store",
        "status": "INACTIVE",
        "subscription_type": "Free",
        "features": []
      }
    ],
    "addresses": null
  }
}

UI State

  • Store access_token and refresh_token securely.
  • Store the first vendor_id from data.vendors[0].vendor_id.
  • On this flow verify-otp creates an empty draft vendor for VENDOR users if one does not exist.
  • Use access_token for every subsequent call.
  • If token expires, call POST /v1/auth/refresh with refresh_token.

Store Membership & Roles (Multi-Account Stores)

A single store can be accessed by multiple user accounts. The existing VENDOR authority still grants store access; the backend additionally checks the tb_vendor_user membership row.

RolePermissions in the onboarding flow
OWNERFull access, including go-live, store settings, delivery/payment config.
STAFFCan manage catalog (categories, products, SKUs) and view orders; cannot change store settings, delivery/payment, or go live.
ADMIN / CUSTOMER_CAREFull access to all vendor-scoped endpoints.

All vendor-scoped endpoints now use @vendorPermissionEvaluator for ownership checks; the UI does not need to send a new role or change existing role handling.

End-to-End API Sequence

Step 1  POST /v1/auth/request-otp
        {
          "country_code": "+91",
          "mobile_number": "9912149049",
          "user_role": "VENDOR"
        }

Step 2  POST /v1/auth/verify-otp
        └── store access_token, refresh_token, vendor_id
            (empty draft vendor is created automatically if needed)

Step 3  GET  /v1/business-types
        PATCH /v1/vendors/{vendor_id}/business-type

Step 4  GET  /v1/categories?business_type_id={id}
        PATCH /v1/vendors/{vendor_id}/categories

Step 5  GET  /v1/categories/{category_id}/products
        PATCH /v1/vendors/{vendor_id}/assign/products

Step 6  POST /v1/vendors/{vendor_id}/skus
        (repeat for each SKU)

Step 7  PUT  /v1/vendors/{vendor_id}/checkout_options
        (includes Step 8 payment_options)

Step 9  PUT  /v1/vendors/{vendor_id}
        GET  /v1/social/INSTAGRAM/auth_url?vendor_id={vendor_id}  (optional)
        PATCH /v1/vendors/{vendor_id}/geo/service_area  (optional)

Step 10 POST /v1/vendors/{vendor_id}/go-live

Key Gotchas for UI/UX

  1. Auth first: Every vendor API needs a valid access_token. Complete Step 1 and Step 2 before anything else.
  2. user_role: VENDOR: The request-otp call must include "user_role": "VENDOR" to start the store onboarding flow.
  3. vendor_id from Step 2: verify-otp creates an empty draft vendor and returns the vendor_id in data.vendors[0]. Capture it before Step 3.
  4. Step 3 updates, not creates: Use PATCH /v1/vendors/{vendor_id}/business-type; the vendor already exists after OTP verification.
  5. Snake case everywhere: Backend expects snake_case JSON keys. Convert to camelCase in React state if needed, but send snake_case.
  6. Images as Base64: banner_image and image_path expect Base64 data URIs, not file uploads.
  7. Checkout options combines delivery + payments: Steps 7 and 8 are a single PUT call.
  8. Social OAuth is redirect-based: Instagram connection happens via browser redirect, not an AJAX call.
  9. Going live is a validation + activation: Step 10 is POST /v1/vendors/{vendor_id}/go-live; it validates setup and sets the vendor to ACTIVE/PENDING.
